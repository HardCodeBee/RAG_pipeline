ReAct 失败归因澄清 v002
会话日期：2026-10-20

用户澄清：达到事先约定的检索预算，不能据此认定实验有问题。

纠正此前聊天表述：不能将“本地配置触发退出”直接等同于“我们的实验/实现导致了错误”。退出机制、预算内方法表现、实现与作者代码的差异是三个不同问题。

1. 13 题已执行 5 次搜索、仍申请继续搜索。
   这是冻结 k10_s5 预算下的方法终止失败，应保留空终答/F1=0。
   没有发现控制器在 5 次之前错误停止搜索。这 13 题不能作为“我们的实验有问题”的证据。
   重复查询也消耗检索预算；缓存命中不自动免除一个逻辑检索轮次。
   作者使用不同的动作上限，并不使事先冻结、明确披露的本地 5 次搜索预算无效。

2. 8 题达到 512 token 但未生成完整动作。
   它们是在既定输出预算下的无动作失败。不能仅从截断推断 512 不够或实验有错。
   但作者的 HotpotQA 实现有动作解析失败后的 Action-only 恢复，本地冻结实现没有。
   这是可确认的机制差异；该差异能恢复多少题尚未实验，不能把 8 题全部归因于这项缺失。
   如另行验证，可保留最多 5 次实际搜索，追加动作恢复的生成调用并单独记录费用；不应自动放宽检索预算。

3. 官方 HotpotQA notebook 实际配置。
   官方主循环最多 7 个动作机会，不是“7 次搜索再额外回答”。
   单次 max_tokens=100，编号 Thought/Action，并在对应 Observation 前停止生成。
   解析失败追加只生成 Action 的调用。
   循环耗尽仍未 Finish 时执行空 finish[]，不会保证再生成正确答案。
   工具为 Wikipedia Search/Lookup/Finish；本地是统一 BGE 语料 Search/Finish。
   模型、工具、分词和提示不同，不能仅用官方 100 vs 本地 512 判断限制是否合理。
   官方来源：https://github.com/ysymyth/ReAct/blob/master/hotpotqa.ipynb

4. 对当前成绩的结论。
   当前结果是 ReAct 在已披露的本地资源与预算下的成绩；不能泛化为原论文在 MuSiQue 的复现成绩。
   不能把全部 21 题说成“我们的实现导致”，也不能据此断言 ReAct 核心方法失效。
   其中 13 题明确按预算正常失败；另外 8 题存在应单独核查的官方动作恢复机制差异。
   底层检索困难、推理偏移和数据标注矛盾仍按 v001 报告逐题记录，互不排斥。
